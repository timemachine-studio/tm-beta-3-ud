# TM-02 processing retention and storage lifecycle

Updated 2026-09-07. **TM-02 is incomplete: local controls are implemented, but actual service retention and deletion have not been verified.** TM-00 and TM-01 were checked before changes; their local/source acceptance requirements pass. Neither task established deployed schema, retention settings or processor deletion.

## Current behavior and agreed direction

Signed-in personal chats still automatically use Supabase `chat_sessions` and `chat_messages`. Guest chats use the browser's `chatSessions` localStorage record. Notes use `tm-notes`; sending content to Notes AI still sends it to a provider. AI memories are a separate cloud store. Group conversations are a cloud collaboration exception.

D1 remains the target: free history on-device, paid history on-device by default, optional cloud sync only after verified paid entitlement and explicit consent. Selecting PRO and signing in do not grant sync consent. These storage changes belong to TM-05/TM-15; TM-02 does not replace the repository or silently move legacy data into the unsafe whole-archive localStorage path. No tables or existing user data were deleted.

The signup disclosure now states the current signed-in cloud behavior. Privacy/account copy distinguishes device data, cloud history, processor data and shared records. It no longer promises device-only storage, daily deletion of rate-limit rows or immediate removal of every copy. These edits describe this checkout; no deployment was made or inspected.

## Local controls and deployment boundary

`api/_lib/retention/policy.ts` defines application limits. The `durableProcessingAvailable()` gate that rejected every new background PRO run with `503 RETENTION_UNVERIFIED` was **removed on 2026-09-08 at the owner's instruction**: beta testers need PRO to work, and a permanently closed gate is not a retention control. `/api/pro-generation` now dispatches runs normally.

The retention facts below are unchanged by that removal: Trigger.dev payload, output, checkpoint and stream deletion is still unverified, so PRO prompts and completions reach a processor whose deletion behaviour we have not confirmed. The bounded expiry helpers (`proContentExpired`, recovery/abandoned/max-age windows) and the cleanup hook still apply to our own rows. Do not describe PRO processing as retention-verified in user-facing copy until the TM-02.5 checks are done.

`api/_lib/retention/cleanup.ts` operates only on the existing PRO and MCP processing tables. It attempts each cleanup phase and returns a fixed failure identifier if any phase fails. It never touches saved chat history, notes, memories, attachments or subscription state. It can run repeatedly; content expiry is anchored to creation/terminal timestamps, not read time. This source change does not make direct Supabase owner reads expire: deployed RLS and deletion must be verified before enabling durable runs.

`POST /api/retention-cleanup` requires a server-only `RETENTION_CLEANUP_SECRET` of at least 32 characters, a matching bearer token, `RETENTION_CLEANUP_ENABLED=true`, and a service-role key. It defaults to disabled. No cron/scheduler was installed in Vercel, Trigger or Codex, and none of these settings was added to `.env`. This avoids silently purging legacy beta processing data. An operator must first test the hook on synthetic staging rows, then authorize and monitor a scheduler. Proposed cadence: every 5 minutes; physical database scrubbing target is the logical expiry plus one cadence, with failures alerting immediately. This is not a verified production SLA.

PRO completion now checks that a running, non-expired row was actually updated before emitting `pro_done`. Late completion cannot restore scrubbed output. Scrubbed receipts stay expired even when the database trigger advances `updated_at`; a regression test covers this. Stored/streamed worker failures use fixed codes, not arbitrary upstream text. The current worker gate also blocks already-queued invocations before model processing, but it cannot retroactively prevent a payload already being held by Trigger.

Account deletion now checks processor-linked PRO rows before destructive steps. If processor removal is unresolved, it preserves the account and mapping for support. Storage deletion walks bounded pages/folders and surfaces failures. Supported database failures (including missing schema) preserve auth; profile/auth deletion only follow successful cleanup. This is a safer partial implementation, not verified whole-account erasure. Group/support/dormant document data and in-flight direct requests still need the full schema and lifecycle audit. No account-deletion operation was run against a real user.

## Existing-beta migration specification

This is the required migration protocol for TM-05/TM-15, not a new storage adapter implemented in TM-02.

1. Identify the owner and local workspace. Present the current cloud inventory without silently assigning another shared-device user's notes/history. Keep legacy cloud data recoverable while importing.
2. Download bounded batches using stable IDs, timestamps and revisions. Include attachment manifests, missing-blob reports and a versioned export manifest with counts and content digests. Offer a downloadable backup before any purge.
3. Import into the transactional IndexedDB repository, then read back every imported record/blob and compare IDs, revisions, counts and digests. Persist the migration receipt atomically with the import. An interrupted import resumes without duplicating or deleting data.
4. Only after verification, switch personal-history writes to device storage for free and opted-out accounts. Test old clients and direct cloud consumers so they cannot continue silently uploading. A failed import keeps the source and produces a visible recovery action; do not route the whole archive into localStorage to bypass TM-05.
5. Retain eligible paid cloud history only after a current server-verified entitlement and explicit opt-in setting with version/time and selected history scope. No billing/persona inference. TM-03 and TM-15 remain required before paid sync is enabled.
6. Give beta users notice and an explicit removal/export path. Do not start a universal purge countdown until the working import/export flow and notice are verified. The paid disable/expiry planning default remains a configurable 30-day download grace with no new agent cloud reads/writes, then purge cloud records/indexes; local copies remain.
7. Rehearse export → interrupted import → retry → read-back → chosen cloud deletion → stale-device reconnect on two synthetic accounts. Check that old clients cannot resurrect removed chats. No blanket table drop, silent mass deletion or email campaign is authorized by this document.
