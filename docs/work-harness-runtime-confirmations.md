# Private runtime confirmation ledger · 2026-09-29

This is a local, service-only persistence slice. It is not connected to an API route, browser approval control, scheduler or OpenHands transport. Every recorded intent has `delivery_status=blocked`. No SQL migration has been applied and no remote execution has been tested.

OpenHands' SDK derives pending actions from unmatched events on the active conversation branch. Its current Agent Server confirmation endpoint accepts a boolean and reason, without an action ID/set or conditional head revision. A recent event page cannot prove what acceptance would execute. Do not feed event-history pages into this ledger or send recorded approvals to that endpoint.

`runtimeConfirmation.ts` accepts an internal trusted-snapshot contract requiring AlwaysConfirm, waiting status, a branch head and a complete ordered action set. A future capture adapter must prove those assertions. There is no such adapter yet. Supported categories are terminal, file editor, task tracker and finish; unknown actions fail closed. Raw arguments, commands and reasoning are never stored. A separate server secret produces a keyed canonical fingerprint of execution payloads, conversation, head and order. Tool categories are private metadata, not sufficient information for meaningful user consent.

The proposed sixth migration, `20260928000000_work_runtime_confirmations.sql`, must be applied explicitly after `work_runtime_handoff.sql` and the preceding four harness migrations. It adds a service-only table and review/decision functions. Reviews bind owner, task generation/revision, connection, conversation and live model grant, require an already started launch and expire within five minutes or grant expiry. Identical decision requests return the same blocked intent; conflicting requests cannot overwrite it. New captures invalidate older reviews. Stop/task changes, binding authority changes, connection configuration changes and entitlement changes invalidate pending and decided records. Natural entitlement/grant/review expiry is checked on every read/decision; expiry does not rely on a scheduled cleanup job. A task can retain at most 100 records.

Optional server configuration: `TM_WORK_CONFIRMATION_LEDGER_ENABLED=false` by default; `TM_WORK_CONFIRMATION_SECRET` is a separate random secret of 32–256 characters. These settings do not enable execution or expose a browser capability. Keep the ledger disabled until the migration and its permission/concurrency behavior have been verified on an explicitly authorized staging database.

Verification uses local mocks for owner/entitlement/binding/RPC boundaries and exercises keyed fingerprints, canonicalization, action order, private-data redaction, malformed payloads, expiry/revocation and identical intent retries. The SQL has not been executed against PostgreSQL. Database privilege, rollback, concurrent Stop/revocation and lost-response acceptance tests remain required before enabling this slice. No deployment, grant, credential, schedule or paid call was made.

A rollback-only [staging canary](../supabase/tests/work_runtime_confirmations_canary.sql) now exercises the proposed migration after all six Work migrations: pre-start denial; owner, revision, connection and grant binding; blocked delivery; identical capture and decision retries; changed-action invalidation; expiry; grant rotation; connection and entitlement revocation; Stop invalidation; and browser-role privilege denial. It uses a quiescent staging account and synthetic identifiers, then rolls back. It has **not** run against PostgreSQL: the local Docker engine did not respond, and no staging database change was authorized. Concurrency and real upstream acceptance remain separate gates.

For an explicitly approved staging run, use `psql -v ON_ERROR_STOP=1 -f supabase/tests/work_runtime_confirmations_canary.sql` after applying the six migrations and selecting a quiescent account. Stop on the first SQL error and inspect the transaction result before relying on the checks. The file itself starts a transaction and ends with `rollback`.

A local database lease alone cannot provide that remote atomicity.
